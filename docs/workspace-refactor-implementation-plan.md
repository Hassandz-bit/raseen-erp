# خطة إعادة هيكلة مساحة العمل وتنظيف التكرارات

## النطاق والقرار

الخطة تعالج تكرار الواجهات فقط. لا تشمل تعديل مخطط البيانات أو الترحيلات أو عقود tRPC أو سياسات العزل أو دورة التجارة والتوزيع والمالية. يظل **Nawa AI** تحليلياً ومحكوماً، و**Nawa Flow** خريطة عمليات داخل مساحة العمل، بينما تنتقل المعاملات إلى وحداتها التشغيلية الفعلية.

> المدة التقديرية: **9–11 أيام عمل** لتنفيذ متدرج مع مراجعة واختبار بعد كل مرحلة. هذه مدة تخطيط وليست التزاماً زمنياً؛ تتغير إذا كشف نقل الواجهات اعتمادات خفية.

## البنية النهائية المستهدفة

```text
Home / لوحة التحكم
  └── KPIs + تنبيهات + روابط انتقال إلى الوحدات

Workspace / مساحة العمل
  ├── Nawa AI (AIChatBox + مؤشرات التحليل المصرح بها)
  ├── Nawa Flow (خريطة عمليات ووحدات)
  └── تنبيهات مرتبطة بالتحليل فقط

الوحدات التشغيلية
  ├── /commerce?tab=inventory|sales|purchases
  ├── /manufacturing
  ├── /distribution (وتحته /driver)
  ├── /finance
  ├── /hr (وتحته /self-service)
  └── /retailer و/b2b-orders تحت Nawa Retail
```

## الجدول الزمني المقترح

| المرحلة | المدة التقديرية | المخرجات القابلة للقياس | نقطة الاستعادة |
|---|---:|---|---|
| 0. تجميد خط الأساس | نصف يوم | اختبار كامل، خريطة مسارات، قياس حجم الصفحات، تقرير الاعتمادات. | قبل أي تعديل |
| 1. مصدر تنقل موحد | يوم واحد | `appNavigation.ts` واحد مستخدم في Home وDashboardLayout. | بعد توحيد التنقل |

| 3. ترحيل الملخصات | يوم ونصف | بطاقات وتقارير الملخص داخل لوحة التحكم أو `/reports`، بلا نسخة ثانية في Workspace. | بعد ترحيل الملخصات |

## خطوات برمجية دقيقة

### 1. إنشاء تعريف تنقل واحد

1. إنشاء `client/src/config/appNavigation.ts` لتصدير نوع `NavigationItem` وقائمتين: `primaryNavigation` و`contextualNavigation`.
2. إعطاء كل مدخل حقولاً صريحة: `id` و`labelKey` و`icon` و`href` و`group` و`requiresModule` و`roleScope`.
3. استبدال مصفوفتَي `navItems` في `Home.tsx` و`menuItems` في `DashboardLayout.tsx` بهذا التعريف، مع بقاء قواعد الرسم البصرية داخل المكوّنين فقط.
4. تسمية `/workspace` بـ«مساحة العمل» في التنقل، مع إبقاء «Nawa AI» عنواناً داخلياً للمساحة لا مدخلاً موازياً.
5. إضافة اختبار وحدة يثبت أن المداخل العليا تظهر بترتيب ومفتاح ومسار واحدين في الغلافين.

### 2. فصل مسؤوليات Workspace

1. استخراج محتوى الذكاء الاصطناعي من `Workspace.tsx` إلى `client/src/features/workspace/AiWorkspace.tsx`، ويشمل اختيار المجال و`AIChatBox` ومؤشرات التحليل المصرح بها فقط.
2. إبقاء `NawaFlow` في `client/src/features/workspace/FlowWorkspace.tsx` أو استعمال المكوّن الحالي عبر غلاف صغير، مع تبويب أو رابط `?view=nawa_flow` داخل مساحة العمل.
3. حذف `OperationsPanel` بعد التأكد من أن كل إجراء من `erp.operations.create` له واجهة تشغيلية بديلة في التجارة أو المالية أو HR؛ لا يحذف العقد الخادمي في نفس Pull Request.
4. إزالة `OperationalOverview` و`InsightsPanel` و`CommerceDocumentsPanel` من Workspace **فقط بعد** نقل المقاييس والتصديرات المستخدمة إلى لوحة التحكم أو صفحة تقارير صريحة.
5. تقليل `Workspace.tsx` إلى مسؤول اختيار العرض وتحميل bootstrap وحراسة صفحة مساحة العمل.

### 3. ترحيل المؤشرات والتقارير بلا تكرار

1. تحديد لكل بطاقة مصدر واحد: مؤشرات المبيعات والمخزون والمالية في `Home` أو `/reports`، ولا تعرض مرة ثانية في Workspace.
2. نقل مولدات `workspaceSummaryExport` و`workspaceReportExport` إلى `client/src/lib/dashboardReportExport.ts` إذا كانت ملكاً للوحة التحكم، ثم تحديث الاستيرادات والاختبارات.
3. إنشاء `/reports` فعلي فقط إذا كان التقرير يحتاج شاشة تشغيلية كاملة؛ وإلا تبقى بطاقة لوحة التحكم مع إجراء «عرض التقارير».
4. التحقق أن كل استعلام tRPC حُذف من Workspace لا يزال مستخدماً أو يحذف معه بعد فحص `grep` والاختبارات.

### 4. إزالة `Home.ModuleView` بأمان

1. إضافة دعم تبويب عميق للوحدة التجارية، مثل `/commerce?tab=inventory` و`/commerce?tab=sales` و`/commerce?tab=purchases`، عبر قراءة `URLSearchParams` والتحقق من القيم المسموحة.
2. تعيين الروابط في تعريف التنقل المركزي: المخزون والمبيعات والمشتريات إلى تبويبات Commerce، المالية إلى `/finance`، الموارد البشرية إلى `/hr`، والتصنيع والتوزيع إلى مساراتهما القائمة.
3. تحويل بطاقات وإجراءات `Home` إلى روابط تنقل فقط؛ لا تنشئ سجلات أو تعرض بيانات ثابتة قابلة للتعديل.
4. إضافة اختبارات لكل رابط عميق، ثم حذف `ModuleView` و`sectionCopy` و`moduleViewCopy` و`moduleViewUiCopy` والاستيرادات والاختبارات التي أصبحت بلا مالك.
5. تشغيل `pnpm check` مباشرة بعد الحذف؛ ثم `pnpm test --run client/src/pages/Home.navigation.test.ts client/src/pages/CommerceInventory*.test.tsx` قبل متابعة أي نقل آخر.

### 5. تنظيم الإعدادات والمداخل السياقية

1. يبقى قسم الاشتراكات في `Settings` للعرض المختصر والحالة فقط، ويقود زر «إدارة الوحدات» إلى `/modules`؛ لا تكرر بطاقات التفعيل والمقارنة داخل الإعدادات.
2. تظهر `/driver` من داخل التوزيع أو من قائمة سياقية بعد التحقق من دور السائق، ولا تظهر في التنقل الإداري العام.
3. تظهر `/self-service` من HR أو من ملف الموظف، ولا تظهر كبديل لمركز HR الإداري.
4. يجمع `/retailer` و`/b2b-orders` تحت عنصر Nawa Retail مع تمييز «بوابة التاجر» و«مركز المورد» وفق الدور.

## استراتيجية الاختبار والاستعادة

| نوع التحقق | شرط القبول |
|---|---|
| TypeScript | `pnpm check` ناجح بعد كل مرحلة حذف. |
| تنقل | كل مدخل مركزي يفتح مساراً واحداً صالحاً، ولا يبقى مدخلان لنفس الوظيفة. |
| الصلاحيات | روابط الدور الفرعي لا تكشف بيانات أو إجراءات عند فتح المسار مباشرة. |
| i18n | عدم ظهور نص عربي ثابت في الفرنسية والإنجليزية، واتجاه صحيح في RTL/LTR. |
| بصري | لقطة Home وWorkspace وCommerce وFinance على سطح المكتب والهاتف بعد كل انتقال رئيسي. |
| انحدار | `pnpm lint` و`pnpm test` و`pnpm build` قبل قرار RC. |

لا تُنفذ عمليات SQL أو ترحيلات. تحفظ نقطة استعادة قبل بداية كل مرحلة، ويستخدم الاسترجاع إلى آخر نقطة مستقرة فقط إذا ظهر كسر لا يمكن إصلاحه بتعديل موجه.

## قرارات الاعتماد المطلوبة

يتطلب بدء التنفيذ اعتماد ثلاثة قرارات: جعل «مساحة العمل» الاسم الرسمي لمدخل `/workspace`، نقل التقارير العامة إلى لوحة التحكم أو صفحة تقارير مستقلة، وإزالة الإنشاء العام متعدد الوحدات من Workspace بعد التحقق من البدائل التشغيلية لكل إجراء.
